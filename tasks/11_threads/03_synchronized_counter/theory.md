# Разбор задания

## Гонка данных

`value++` — это не одна операция, а три:

1. прочитать `value` в регистр;
2. прибавить единицу;
3. записать обратно.

Если два потока выполняют шаги вперемешку, оба могут прочитать одинаковое старое значение, и одно приращение потеряется. Это называется гонкой данных (race condition).

## synchronized

```java
synchronized void increment() {
    value++;
}
```

Модификатор `synchronized` у метода означает: перед входом поток захватывает монитор объекта (`this`), а при выходе отпускает. Пока один поток внутри, другой ждёт. Операция становится **атомарной** относительно других синхронизированных методов того же объекта.

Альтернатива — синхронизированный блок:

```java
void increment() {
    synchronized (this) {
        value++;
    }
}
```

## Что synchronized не делает

- Не ускоряет код: блокировка стоит времени.
- Не защищает от гонок на других объектах: синхронизация работает только вокруг одного монитора.
- Не заменяет `volatile`: `volatile` обеспечивает видимость, но не атомарность `value++`.

## Атомарные классы

Пакет `java.util.concurrent.atomic` содержит готовые решения:

```java
AtomicInteger counter = new AtomicInteger();
counter.incrementAndGet();
```

`incrementAndGet` атомарен без явной блокировки (обычно через CAS). В этом задании нужен именно `synchronized` — чтобы понять механизм.

## get() и видимость

`get()` не синхронизирован. После `join()` оба потока завершены, и все записи видны основному потоку: `join()` создаёт отношение happens-before. В общем случае `get()` тоже стоило бы синхронизировать или объявить `value` как `volatile`.

## Частые ошибки

| Ошибка | Что происходит |
| --- | --- |
| Нет `synchronized` | Потерянные обновления, нестабильный результат |
| `synchronized` на разных объектах | Блокировки не пересекаются |
| `volatile int value` | Видимость есть, атомарности нет |
| Два потока делят один счётчик без блокировки | Гонка |
| Ждать ровно `2 * K` без синхронизации | Тест может «повезти», но это баг |
