# Разбор задания

## Исключения

Исключение — объект, сигнализирующий об ошибке во время выполнения. Если его не обработать, программа завершается и печатает стек вызовов.

```java
int x = 5 / 0;   // ArithmeticException: / by zero
```

## try/catch

```java
try {
    // опасный код
} catch (ArithmeticException e) {
    // что делать при ошибке
}
```

Поток управления:

1. Выполняется блок `try`.
2. Если исключение возникло, остаток `try` пропускается.
3. Управление переходит в подходящий `catch`.
4. Если исключение не возникло, `catch` пропускается.

## Тип исключения

`ArithmeticException` — **непроверяемое** (unchecked) исключение: компилятор не требует его обрабатывать. При делении на ноль целых чисел JVM выбрасывает именно его.

Для вещественных чисел деление на ноль исключения не даёт:

```java
double d = 5.0 / 0.0;   // Infinity
```

Поэтому задача сформулирована для `int`.

## Почему не проверять b == 0 заранее

Можно написать `if (b == 0) { ... } else { ... }` — это тоже корректно. Но цель задания — познакомиться с `try`/`catch`. В реальном коде для деления часто проверяют условие, а исключения ловят там, где ошибка действительно непредвиденна.

## Ловля слишком широкого типа

```java
catch (Exception e) { ... }   // работает, но скрывает все ошибки
```

Так делать не стоит: легко проглотить `NullPointerException` и другие настоящие баги. Ловите максимально конкретный тип.

## Частые ошибки

| Ошибка | Что происходит |
| --- | --- |
| Нет `catch` | Программа падает с `ArithmeticException` |
| `catch (Exception e)` | Слишком широко, скрывает другие ошибки |
| Пустой `catch` | Ошибка молча игнорируется |
| `catch (ArithmeticException)` без переменной | Ошибка компиляции: нужен параметр `e` |
| Деление `double` в задаче | Не бросает исключение, тест на ноль не сработает |
